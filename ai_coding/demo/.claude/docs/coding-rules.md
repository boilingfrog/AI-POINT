# 通用编码纪律

适用于本项目所有开发任务。核心信念：**删多于增——复杂度会累积成灾难**。

1. **先读后写**：改文件前读懂它和相邻层（哪一层负责什么），别基于片段就动手，易加重复逻辑。
2. **先想再写**：需求模糊先陈述假设和权衡；先定位改动应落在 transport/service/dao/model
   哪一层，困惑就停下来问。
3. **简洁**：写解决当前问题的最少代码，不过早抽象、不推测性错误处理（复制两次以上再抽象）。
4. **精准修改**：diff 越小越好，不动没让你动的东西，匹配现有风格，不顺手重排/重命名无关代码。
5. **验证**：改 bug 先写能复现的测试再修；改动前后都跑 `make lint && make vet && make test`。
6. **目标驱动**：只做需求要求的改动，先定义清楚"做完的标准"，多步任务先规划再动手。
7. **调试**：读完整错误信息；先稳定复现；一次只改一处；别猜根因，用日志/测试定位。
8. **依赖**：**本项目零外部依赖，只用标准库**——禁止引入任何需 `go mod download` 的库
   （离线约束）。用标准库能解决的别造轮子、别加依赖。
9. **沟通**：说清做了什么、为什么；不确定处标注出来；commit 信息具体（`feat: 校验发放金额`
   而非 `修改`）。
10. **常见失败模式**（主动规避）：
    - 跨层反向依赖（如 dao 反过来 import service）
    - 漏 gofmt / 漏跑测试
    - 金额用了 float，或漏校验金额 > 0
    - 在 handler 里写业务逻辑（应在 service 层）
    - 范围蔓延、顺手大重构、凭记忆编造 API
