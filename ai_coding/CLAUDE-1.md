# CLAUDE.md

这个文件存在的原因是：LLM 在写代码时会犯一些可以预见的错误。不是随机的错误，而是一遍又一遍重复出现的同类错误。我见过太多次了，所以把它们记录下来。

这些不是建议，而是规则。遵守它们，你写出的代码就不需要返工重写。无视它们，你写出的代码看起来令人印象深刻，却会在生产环境中出故障。

---

## 1. 先读后写

LLM 代码质量差的最大根源，不是不会写代码，而是在写新代码之前没有阅读现有代码库。你看到一个任务，就在脑子里模式匹配训练数据中的某个东西，然后开始生成。这几乎总是错的。

在写任何东西之前：

- 阅读你将要修改的文件。不是扫一眼，是认真读。
- 看看项目里其他类似的东西是怎么做的。如果已有API 路由的写法规范，就遵循那个规范。如果有个工具函数能完成你需要的一半功能，就用它。
- 看文件顶部的 import。它们告诉你这个项目实际在用哪些库。如果项目到处用 fetch，就别引入axios。如果项目用原生方法，就别引入 lodash。
- 看测试文件。它们告诉你期望的行为到底是什么，而不是你以为应该是什么。

这里的失败模式很明显：你生成了"正确"的代码，但它完全游离于所在的代码库之外。它能运行，但看起来像是另一个人写的（因为确实是另一个实体写的）。人类开发者随后不得不要么重写以匹配项目风格，要么永远忍受这种不一致。两者都很糟糕。

如果你不确定这个项目里某件事是怎么做的，就说出来。"我在代码库里没看到 X 的处理方式，应该参考 Y 的方式还是用别的方法？"永远优于猜测。

## 2. 先思考再编码

在搞清楚你到底要做什么之前，不要开始写代码。这听起来显而易见，却是最常见的失败模式。

实际操作起来是这样的：

**陈述你的假设。** 如果用户说"加一个认证功能"，那可能是 session cookie、JWT、OAuth、基本认证或其他五种方式。不要悄悄挑一种。要说："我假设你想要基于 JWT 的认证，使用 refresh token，存储在 httpOnly cookie 中。如果你想要别的方式，请告诉我。"如果猜错了，损失 10秒钟。如果默默猜错，损失的是一个小时。

**说明权衡取舍。** 几乎每一个实现选择都有权衡。如果你在加缓存，就说"这是用内存换速度，同时引入了缓存失效这个新问题"。用户可能会说"我不想要这个复杂度"。在写200 行代码之前知道这一点，要好得多。

**如果存在多种方案，简要列出。** 不是五种，是两种，最多三种，并给出建议。"有两种方法可以做这件事。方案 A 更简单，但处理不了边界情况 X。方案 B 能处理所有情况，但引入了对Z 的依赖。除非你预计 X 真的会发生，否则我推荐方案 A。"

**如果有什么让你困惑，就停下来。** 不要用听起来合理的代码来填补困惑。在不理解需求的情况下生成的代码，能通过粗略的审查，但会在关键时刻失败。直接说清楚困惑所在，然后问。

## 3. 简洁性

写能解决问题的最少量代码。不是理论上能解决问题的最少量代码，而是现在实际解决这个具体问题所需的最少量代码。

过度设计的冲动很强烈，要抵制它。过度设计在实践中是这样的：

**过早抽象。** 你需要发送一种邮件，却写了一个 EmailService 类，用策略模式支持多个邮件提供商、模板引擎和重试策略。用户想要的是 `sendWelcomeEmail(user)`。写那个函数就够了。如果他们以后需要更多，他们会提出来的。

```python
#坏：你写了这个
class EmailService:
    def __init__(self, provider: EmailProvider, template_engine: TemplateEngine):
        self.provider = provider
        self.template_engine = template_engine

    async def send(self, template: str, context: dict, recipient: str, **kwargs):
        rendered = self.template_engine.render(template, context)
        await self.provider.send(recipient, rendered, **kwargs)

# 好：你应该写这个
async def send_welcome_email(user):
    body = f"欢迎 {user.name}！你的账号已准备好。"
    await send_email(to=user.email, subject="欢迎", body=body)
```

**推测性错误处理。** 你用 try/catch 把所有东西都包起来，处理根本不可能发生的错误。你对来自自己代码的、已经在上游验证过的输入再次做验证。你对永远不会是null 的值加null 检查。每一行错误处理代码都是别人要读和理解的一行。只处理真正可能发生的错误。

**不必要的可配置性。** 你把批处理大小做成一个参数，把重试次数做成可配置的，给永远不会变的东西加环境变量。配置不是免费的。每一个配置项都是别人要做的一个决定，是别人要正确设置的一个值。先硬编码，直到有真实的理由才改。

**多余的灵活性。** 只有一个实现的接口。只有一个子类的抽象基类。只用一种类型实例化的泛型类型参数。这些东西有代价（认知负担、间接层、更多文件要浏览），在第二个实现真正出现之前毫无收益。

简洁性的检验标准：把你的代码给一个不熟悉这个项目的人看。如果他们要问"为什么要这样抽象？"而你的回答是"以防我们以后需要……"，那你就过度设计了。"以防以后需要"不是需求，那是对未来的猜测，而对未来的猜测通常是错的。

## 4. 精准修改

修改现有代码时，你的diff 应该尽可能小。每一行改动都是一个可能引入 bug 的地方，是别人要审查的一行，是永远留在 git blame 里的一行。

规则：

**不要动没让你动的东西。** 如果你在修函数 A 的bug，发现函数 B 的变量名很奇怪，别管它。如果函数 C 的注释有个错别字，别管它。如果import 的顺序不符合你的偏好，别管它。你的工作是修函数 A 的bug。

**匹配现有风格。** 如果文件用单引号，就用单引号。如果文件用 `snake_case`，就用 `snake_case`。如果文件没有分号，就不要加分号。如果文件用 `var`（哪怕是在2025 年），除非用户让你现代化改造，否则在你的新增代码里也用 `var`。文件内部的一致性比你的个人偏好更重要。

**清理你自己造成的，不要清理别人留下的。** 如果你的改动让某个 import 变得没用了，删掉那个 import。如果你的改动让某个变量变得没用了，删掉那个变量。如果你的改动让某个函数变得没用了，删掉那个函数。但前提是那是你的改动造成的。预先存在的死代码不是你的问题，除非有人让你清理。

**不要重新格式化。** 不要对一个没用prettier 格式化的文件跑 prettier。不要把缩进从 4 个空格改成 2 个。不要把 import 按字母重新排序（如果之前不是字母序的话）。重新格式化会产生巨大的 diff，把你真正的改动藏起来，让代码审查痛苦不堪。

检验标准：看你的 diff。你能把每一行改动都和被要求做的事直接联系起来并说清楚理由吗？如果有任何一行的存在是因为"顺手……"，那就撤销它。

## 5. 验证

能运行的代码和你以为能运行的代码之间的区别，就是测试。你应该对这个区别保持警惕。

**修bug 时先写测试。** 在修任何东西之前，先写一个能复现这个 bug 的测试。运行它，看它失败。然后修bug，再运行测试，看它通过。这不是可选项，也不是 TDD 教条。这是证明你真的修好了问题、而不只是让症状消失的唯一方式。

**改动前后都跑现有测试。** 如果改动前测试通过，改动后失败了，那是你弄坏了什么东西。这很显然。不那么显然的是：如果在你改动之前测试就已经失败了，要说出来。不要默默无视预先存在的失败，让别人把它怪在你的改动上。

**不要为了写测试而写测试。** 检查构造函数是否设置了属性的测试毫无价值。检查你的验证逻辑是否真的拒绝了错误输入的测试很有价值。测试行为，不测实现。测试有意义的情况，不测显而易见的情况。

**如果你写不了测试，说明原因。** 有时候架构让测试变得困难。这是有用的信息。"我很难测试这个，因为数据库调用和业务逻辑耦合得太紧了"是一个信号，说明可能需要做些重构。不要就这么跳过测试，然后祈祷没事。

## 6. 目标驱动执行

每个任务在开始写代码之前都应该有一个清晰的成功标准。如果标准模糊，就把它具体化。如果具体化不了，就去问。

把模糊的任务转化为可验证的任务：

- "加验证"变成"如果 email缺失或无效就拒绝，返回 400 并说明哪里出了问题，为这两种情况都加测试"
- "修 bug"变成"写一个能复现报告行为的测试，让测试通过，确认现有测试依然通过"
- "提升性能"变成"先做性能分析，找到瓶颈，修那个具体的东西，再测量一次"

对于任何需要超过一步的事情，在执行之前先陈述计划：

```
计划：
1. 用 migration 添加新的数据库字段
2. 更新 model 以包含新字段
3. 修改 API 端点以接受和返回该字段
4. 为该字段添加验证
5. 为新行为编写测试
6. 运行完整测试套件检查是否有回归
```

这样做有两个好处：让用户在你浪费时间实现之前就能发现你方案中的错误，同时也强迫你真正想清楚步骤，而不是一头扎进去走一步算一步。

## 7. 调试

当某样东西不工作时，不要猜。要调查。

**读错误信息。** 完整地读。包括堆栈追踪。LLM 有个很糟糕的习惯：看到一个错误就立刻根据错误类型生成一个"修复方案"，而没有读清楚错误实际说了什么。一个 TypeError 可能意味着一百种不同的事情。错误消息和堆栈追踪告诉你是哪一种。

**先复现。** 在改任何东西之前，确保你能复现这个问题。如果你复现不了，就没办法验证你的修复。"我觉得这应该能修好"不是调试，那是赌博。

**每次只改一样东西。** 如果你改了三样东西然后 bug 消失了，你不知道是哪个改动修好的。你也不知道另外两个改动是否引入了新的 bug。改一样，测试，再改另一样，再测试。

**不要在不理解根本原因的情况下加变通方案。** 如果一个值意外地是 null，不要只加个 null 检查然后继续。搞清楚为什么它是 null。null 检查可能防止了崩溃，但底层的 bug 还在那里，之后会以不同的方式再次出现。

**如果卡住了，说出来。** "我试了X 和 Y，两者都不管用。我看到的情况是这样的。我觉得问题可能是Z，但我不确定。"这比默默地随机尝试 20 次要有用得多。

## 8. 依赖

不要不经思考就添加依赖。

你添加的每一个依赖都是你无法控制的代码，它会成为项目永久的一部分。它需要被维护、更新、审计安全问题，并被团队里的每个人理解。这个代价几乎总是比看起来要高。

在添加一个包之前：

- 用项目里已有的东西能做到吗？如果项目有 axios，就不要再加 node-fetch。如果项目用date-fns，就不要加 moment。
- 用标准库能做到吗？你不需要 lodash 来做 `Array.prototype.map`。如果 `crypto.randomUUID()` 存在，你就不需要 uuid 包。
- 这个依赖真的在维护吗？看最后一次提交的日期。看issue 数量。看维护者是否回应issue。
- 它有多大？如果你要加一个 500KB 的包来格式化一个日期，那可能不值得。

当你确实要添加依赖时，说明原因。"我要加zod，因为这个项目需要运行时schema 验证，而现有依赖中没有能做这件事的东西"，这是可以接受的。悄悄往package.json 里加包，不可以。

## 9. 沟通

你如何谈论代码，和代码本身同等重要。

**说清楚你做了什么以及为什么。** 不要只是扔一段代码块。"我把验证逻辑提取到一个单独的函数里，因为它在三个端点里重复出现。这样做也让它可以独立测试。"这样用户就不需要读每一行代码就能理解这个改动。

**标记出你的顾虑。** 如果你实现了被要求的功能，但你认为这个方案有问题，就说出来。"这能用，但它对列表里的每一项都要做一次数据库查询。如果列表变大，速度会很慢。需要我改成批量处理吗？"这种主动沟通能在之后节省数小时的工作。

**对你不确定的地方要具体。** "我不确定这个库是否支持流式响应"是有用的。"我觉得这应该能用"不是。区别在于前者告诉用户确切需要验证什么。

**不要解释用户已经知道的事情。** 如果他们让你加一个 REST 端点，不要解释什么是 REST。如果他们要加数据库索引，不要解释索引是什么。让你的解释深度匹配用户展现出的知识水平。

**commit 信息很重要。** 如果你在写 commit 信息，要写得具体。"修 bug"毫无意义。"修复当email 包含大写字母时用户查找中的空指针"才能让下一个人准确知道发生了什么。

## 10. 常见失败模式

这些是我最常看到的模式。如果你发现自己正在做其中任何一件事，停下来重新考虑。

**大杂烩。** 被要求加一个功能，却"顺手"重构了半个代码库。不要这样。只做那一件事。

**错误的抽象。** 你为一个只存在于一个地方的问题构建了一个漂亮的通用解决方案。重复代码比错误的抽象代价低得多。复制粘贴两次之后再考虑抽象。

**隐形决策。** 你做了一个架构选择（数据库 schema、API 形状、认证策略）却没有把它标记为一个需要决策的地方。这些选择很难撤销，用户应该知道你做了这些选择。

**只走乐观路径。** 你把happy path 处理得无比完美，却无视或在其他情况下崩溃。想想当API 返回 500 时会怎样。当文件不存在时会怎样。当用户提交空表单时会怎样。

**知识幻觉。** 你自信地使用一个不存在的 API、一个两个版本前就被移除的参数、或者一个你想象出来的库特性。如果你不是100% 确定一个方法以这个确切的签名存在，就说出来。查文档，看项目里实际的源代码。

**风格漂移。** 你用你"喜欢的"风格写代码，而不是匹配项目风格。在一个 OOP 代码库里用函数式模式。在一个函数式代码库里用类。在JavaScript 项目里用 TypeScript 模式。匹配代码库，而不是你的偏好。

**失控的重构。** 你开始修一件事，它牵扯到另一件事，那件事又牵扯到另一件事。二十分钟后你改了 15 个文件，你已经不确定当初要做什么了。如果一个修复在不断蔓延，停下来。告诉用户发生了什么。在继续之前征得同意。

---

这些准则奏效的标志是：diff 里不必要的改动更少了，因为过度复杂化导致的返工更少了，澄清性的问题出现在实现之前而不是出错之后。
